# ADR-011：剪辑数据交换选 OTIO/EDL，不做剪映草稿

- 状态：已接受
- 日期：2026-07-27
- 相关需求：PRD-REN-006「导出第三方剪辑数据」（P2）

## 背景

PRD-REN-006 要求「导出第三方剪辑数据」，验收标准写的是「由 Exporter 插件
实现」。用户明确点名希望能导到剪映；剪映不行则考虑 OpenCut。

## 调研结论（2026-07）

### 剪映：不可行

- 剪映自 **6.0 起对 `draft_content.json` 加密**，之后连 `draft_meta_info.json`
  也一并加密；当前主线版本已到 **10.x**。
- 社区工具（pyJianYingDraft 等）明确只支持 **5.9 及以下**未加密版本。
- 要支持现行版本，只能内置社区逆向出来的解密/回加密算法。

两条路都不该走：

1. 只支持 5.9 及以下 —— 该版本早已过时，等于没做。
2. 内置解密 —— 这是**绕过第三方软件的技术保护措施**。本项目在 PRD §11 与
   SECURITY 里已明确「不包含反检测、指纹伪装和规避平台风控代码」，对剪映
   的加密同样适用；且加密方案随版本变化，今天能跑明天就废，会变成持续的
   维护负担和用户投诉来源。

### OpenCut：目前也不可行

OpenCut（开源在线剪辑）**尚无可移植的工程文件格式**：项目状态锁在浏览器的
IndexedDB/OPFS 里，可以导出成品视频，但导不出时间线。社区 Issue #719 正在
请求一个带版本化 JSON Schema 的工程格式，尚未实现。

等它落地后可以再补一个 exporter —— 那时是开放格式，没有本 ADR 的顾虑。

## 决策

导出 **OpenTimelineIO（OTIO）** 为主、**CMX3600 EDL** 为辅。

- OTIO 是 Academy Software Foundation 的开放标准：纯 JSON、每个对象自带
  版本化的 `OTIO_SCHEMA`、DaVinci Resolve / Premiere / Final Cut / Avid
  都能读。
- EDL 作最大公约数兜底：几乎所有 NLE 都认，代价是只有剪辑点、没有元数据。
- 两者都用标准库生成，**不引入新依赖**（符合本地优先、零依赖的既有取向）。

导出的内容用的是 STEPWORK 独有的数据：精确分析检出的**场景切点**、逐字稿的
**时间戳**（转成时间线 marker）。用户拿到的不是一条空时间线，而是已经切好
段、标好台词位置的工程。

## 后果

- ✅ 用户能把成果带进任何专业 NLE 继续剪，不被单一厂商锁定。
- ✅ 无法律与合规风险，无需跟随剪映版本更新。
- ❌ 无法直接导入剪映 —— 这是剪映加密带来的客观限制，非本项目取舍。
  剪映用户可通过支持 OTIO/EDL 的软件中转，或等 OpenCut 工程格式落地。
- 若将来剪映提供官方导入接口或开放格式，可另开 exporter，不影响本决策。

## 验证

手写的 OTIO 输出已用官方 `opentimelineio` 库实际加载验证：Timeline 结构、
2 个片段的边界（0–3s / 3–7.5s）、marker、总时长均正确解析。该库**仅用于
验证**，未加入项目依赖。
